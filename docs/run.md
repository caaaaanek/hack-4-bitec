# Як запустити: база, бекенд, фронтенд

> Фронтенд — `frontend-proto/` (React + Vite). У `docker compose` він бере всі дані з бекенду: вхід, індекс,
> рекомендації, заходи, хвилі, посилання, анкети, чек-лист, журнал. Без API (`npm run dev`) працює на демо-даних.

## Усе через Docker (одна команда)

```bash
cp .env.example .env     # заповнити POSTGRES_PASSWORD, JWT_SECRET (не коротше 32 символів), DEMO_PASSWORD
docker compose up --build
```

| Що | Адреса |
|---|---|
| Фронтенд (nginx, `/api` проксіюється на бекенд) | http://localhost:8080 — вхід: `leader`, `admin`, `coordinator`, `department`, `auditor`, `wg1`, `staff01`, `expert1`, пароль `DEMO_PASSWORD` |
| API і Swagger напряму | http://localhost:8000/docs |
| Стан (процес + БД) | http://localhost:8080/health, http://localhost:8000/health |

Порядок старту: `db` (healthcheck `pg_isready`) → `backend` (міграції, seed, healthcheck `/health` з БД) → `frontend`.
Файли-докази лежать у томі `evidence`. Почати з чистої бази: `docker compose down -v`, потім `docker compose up --build`.

Перевірити стенд з кінця в кінець (вхід, хвиля за посиланнями, повтор → 409, файл-доказ із sha256, журнал):

```bash
# Окремий проєкт compose: свої томи й БД, демо-стенд не зачіпається. Основний стенд зупиніть (ті самі порти).
docker compose stop
SEED_WITH_WAVES=false docker compose -p smoke up -d --build
python backend/scripts/smoke.py --base http://localhost:8080 --password "$DEMO_PASSWORD"
docker compose -p smoke down -v      # прибрати разом із даними
docker compose start                 # повернути демо-стенд
```

Smoke лише на окремому проєкті (`-p smoke`): він лишає в БД хвилю «Smoke …», файл-доказ і записи журналу,
які не видаляються (журнал незмінний). Якщо в БД є хвилі «(демо)», скрипт зупиняється з кодом 2;
`--force` — запустити все одно.

### За проксі організації

- Під підшляхом (`https://portal.example/imd/`): `ROOT_PATH=/imd` для бекенду; адреси в `/docs` і OpenAPI стануть `/imd/...`.
- Посилання на анкети будуються від `PUBLIC_URL` (`https://portal.example/imd` → `.../s/<токен>`).
- Вхід через SSO: `PROXY_AUTH_ENABLED=true`, `TRUSTED_PROXIES=<IP чи мережа проксі>`, за бажання `PROXY_AUTH_SECRET`.
  Проксі має сам задавати `X-Remote-User` (і `X-Proxy-Secret`) після автентифікації й не пропускати їх від браузера.
  Фронтенд викликає `POST /api/v1/auth/proxy`, коли `GET /api/v1/config` → `auth.proxy: true`.
  Без `TRUSTED_PROXIES` API з увімкненим входом через проксі не стартує.
- Реальна IP клієнта для лімітів спроб береться з `X-Forwarded-For` лише від адрес `FORWARDED_PROXIES` (nginx).
  У compose за замовчуванням це приватні мережі Docker; SSO цим не вмикається. Порт API `8000` опубліковано лише
  на `127.0.0.1`, щоб ззовні не можна було підробити `X-Forwarded-For` в обхід nginx.

## Бекенд без Docker

`cd backend`, далі кроки з [`backend/README.md`](../backend/README.md): venv, alembic, seed, uvicorn на порту 8000.

## Усе одним процесом без Docker

API може сам віддавати зібраний фронтенд (`FRONTEND_DIST`): один процес, один порт, без nginx.

```bash
cp backend/.env.example backend/.env   # DATABASE_URL (PostgreSQL), JWT_SECRET ≥ 32 символи, DEMO_PASSWORD
(cd frontend-proto && npm ci && npm run build)
cd backend && alembic upgrade head && SEED_WITH_WAVES=true python -m app.seed.seed
FRONTEND_DIST=../frontend-proto/dist PUBLIC_URL=http://localhost:8000 uvicorn app.main:app --port 8000
```

Сторінки, `/s/<токен>`, QR `/q/<код>` і `/api/v1` — на тому ж порту, з тими самими заголовками безпеки, що й у nginx.

## Фронтенд

Код — у `frontend-proto/src/` (React + Vite). `npm install`, далі `npm run dev` (http://localhost:5173, `/api` і `/health` проксіюються на `BACKEND_URL`, за замовчуванням http://127.0.0.1:8000) або `npm run build` → `dist/`.
Сторінка сама визначає режим: якщо `GET /api/v1/config` відповідає — вхід і дані з бекенду, інакше демо-дані.

- Через Docker: `docker compose up --build frontend` перезбирає лише фронтенд.
- Без бекенду: `cd frontend-proto && npm run dev` — спершу екран «Сервер недоступний», кнопка «Відкрити демо-режим» дає демо-дані, роль перемикається в меню. Статичний хостинг без `/api` (Vercel) відкриває демо одразу.

Що бачить кожна роль після входу:

| Логін | Екрани |
|---|---|
| `leader`, `leader_a` | огляд (з «Підготуватися до перевірки», брифінгом, сигналами чергового, картками відвертості й підгонки), розклад індексу, динаміка (з розподілом рівнів дочірніх без назв), порівняння, «Що, якщо», рекомендації (прийняти / уточнити / відхилити), трекер, джерела, питання перевірки, звіт, «Що змінилось», реєстр ризиків, навчання |
| `admin` | керування циклом: нова хвиля, відкрити / завершити, учасники й відповідальні за чек-лист, QR для зали (одне на групу), зупинка сканів, автопілот і урна вибраної хвилі, стан інтеграції з Mitra; огляд, розклад, динаміка, порівняння (лише перегляд); питання перевірки, перевірки, «Що змінилось», довідник фактів, реєстр ризиків (імпорт), журнал, перегляди підрозділів, запити другій людині, навчання |
| `auditor` | результати лише на перегляд (огляд, розклад, динаміка, порівняння, «Що, якщо», трекер, джерела), питання перевірки, «Що змінилось»; чек-лист: підтвердження пунктів і лотерея перевірок; журнал з перевіркою ланцюжка й якорем; перегляди підрозділів, запити другій людині (підтвердження відкриття хвилі), урна, реєстр ризиків, навчання. Автопілот аудиту доступний лише через API |
| `department` | заклади по одному, без рейтингу (стартовий екран); огляд, розклад, динаміка, порівняння, «Що, якщо», джерела, питання перевірки й звіт обраного закладу; анкети (конструктор, публікація, нова версія), довідники (перегляд категорій), реєстр ризиків, «Що змінилось», навчання. Типово ввімкнено простий режим: у меню лише заклади, огляд, звіт, анкети й реєстр ризиків |
| `coordinator` | технічний адміністратор: люди й підрозділи |
| `wg1` | чек-лист (стартовий екран: статус, доказ, файл) у відкритій хвилі будь-якого режиму, анкета, мої результати, навчання |
| `staff01`, `expert1` | анкета за обліковим записом, мої результати (з карткою «Навчання» і квитанціями, якщо хвиля з квитанціями), навчання |

Анонімна хвиля проходить за QR: адміністратор створює QR на групу (анкета, підрозділ, скільки людей), показує його на весь екран,
кожен скан `http://localhost:8080/q/<код>` відкриває нову одноразову форму `/s/<токен>` без входу. Рахуються лише подані форми;
відповідей більше, ніж людей у групі, — попередження «можлива накрутка». Щоб QR відкривався з телефона, задайте в `.env`
`PUBLIC_URL=http://<IP комп'ютера в мережі>:8080`, інакше в коді буде `localhost`.

## Асистент (опційно)

Кнопка «Асистент» працює і без моделі (шаблони правил). Модель — будь-який
OpenAI-сумісний `/chat/completions`, наприклад Gemma за шлюзом із ключем. У `.env` (не в `.env.example`, він комітиться):

```bash
LLM_BASE_URL=https://<шлюз>/v1
LLM_API_KEY=<ключ>
LLM_MODEL=gemma4-26b
LLM_ALLOW_EXTERNAL=true   # шлюз поза закритим контуром: без цього бекенд дані туди не відправить
```

За замовчуванням (`LLM_ALLOW_EXTERNAL=false`) модель приймається лише за внутрішньою адресою: localhost, приватна
мережа, ім'я сервісу compose, `*.local`, `host.docker.internal`. Ключ без `LLM_BASE_URL` асистента не вмикає.

Перевірено 18.11 на зовнішньому шлюзі: `gemma4-26b` відповідає українською за 1–3 с і сама викликає інструменти
бекенду (результати, динаміка, заходи), зокрема коректно відмовляє керівнику підрозділу в даних усієї організації.
Інша модель — будь-який OpenAI-сумісний сервер (наприклад, своя Ollama: `http://host.docker.internal:11434/v1`).

Бекенд (`/api/assistant`) пускає лише ролі з доступом до результатів і пише в журнал довжину питання, а не його текст.

## Демо-дані бекенду

`docker compose up` за замовчуванням (`SEED_WITH_WAVES=true`) одразу створює демо-історію:

- особовий склад по 10–15 осіб на підрозділ (`staff01`…`staff75`);
- «Хвиля 1 (демо)», закрита близько пів року тому: «Підрозділ В» має замало відповідей, тож видно поріг k і вторинне приховування;
- рішення `leader` щодо рекомендацій хвилі 1 (прийнято, уточнити, відхилено) і заходи: виконані, у роботі, прострочені;
- «Хвиля 2 (демо)», закрита сьогодні: індекс вищий, рекомендації ще без рішень (їх можна ухвалити на демо).

Повторний старт нічого не дублює: якщо хвилі вже є, історія не додається. Без історії: `SEED_WITH_WAVES=false` у `.env`.

Без демо-даних узагалі (робочий стенд): `SEED_DEMO=false` у `.env` (локально — `python -m app.seed.seed --no-demo`).
Тоді створюються лише чотири анкети з додатків Б і В і два адміністратори (див. нижче). Каталог заходів (Додаток Д)
читається з файлу й доступний завжди. `SEED_DEMO=false` вимикає й `SEED_WITH_WAVES`. На вже засіяній базі нічого не
видаляє: почніть з `docker compose down -v`.

### Перший запуск: два адміністратори

Адміністраторів двоє, і це дві різні людини: **уповноважений** (`admin`: хвилі, учасники, підтвердження нових людей)
і **технічний адміністратор** (`techadmin`, роль `coordinator`: люди й підрозділи). З принципом двох осіб
(`FOUR_EYES_ENABLED=true`, за замовчуванням) одна людина нікого не додасть: облікові записи, які заводить
технічний адміністратор, активує уповноважений, а відкриття хвилі підтверджує внутрішній аудит.

1. `SEED_DEMO=false` → seed виводить у консоль (журнал контейнера `backend`) два одноразові запрошення:
   `Запрошення для admin …` і `Запрошення для techadmin …`. Пароля з env немає. Посилання діє `INVITE_TTL_HOURS` (72 год).
   Повторний запуск нових записів не створює; прострочене запрошення перевидає інший адміністратор
   (`POST /api/v1/admin/users/{id}/invite`), а для першого — `docker compose down -v` і новий старт.
2. Кожен відкриває своє посилання й ставить пароль сам (`POST /api/v1/auth/invite`).
3. Технічний адміністратор заводить підрозділи (`/admin/units`) і людей (`/admin/users`, `/admin/users/import`),
   серед них внутрішній аудит і керівника. Кожному — запрошення, а записи неактивні, доки їх не підтвердить уповноважений
   (`GET /api/v1/admin/approvals` → `approve`).
4. Уповноваженому, що відповідає за один заклад чи департамент, технічний адміністратор ставить `unit_id`: тоді той
   працює лише в цьому підрозділі й піддереві (не обере чужого для хвилі й не побачить чужих хвиль).

Якщо уповноваженого немає зовсім (наприклад, запис заблоковано), технічний адміністратор може створити лише його, і цей
запис активний одразу; будь-кого іншого — 409 `bootstrap_incomplete`.
Локально без Docker: `python -m app.seed.seed --with-waves` (сервер запускати не треба).

Додати ще хвилю до вже засіяної бази (сервер має працювати):

```bash
cd backend
python scripts/demo_wave.py --title "Хвиля 3" --shift 1
# або в контейнері: docker compose exec backend python scripts/demo_wave.py --title "Хвиля 3"
```

Або пройти все через API (Swagger): admin створює хвилю й просить відкрити, auditor підтверджує відкриття, учасники
проходять анкети, робоча група вносить чек-лист з документами, auditor його підтверджує, admin закриває хвилю.

Після хвиль: `GET /api/v1/dashboard` від імені `leader` показує індекс, динаміку, топ-рекомендації, заходи й ризик-сигнали.

Демо-логіни бекенду (пароль у всіх `DEMO_PASSWORD`):

| Логін | Роль | Що може |
|---|---|---|
| `admin` | уповноважений | хвилі, учасники, призначення чек-листа, автопілот, факти, журнал, результати агрегатами; підтверджує нових людей |
| `coordinator` | технічний адміністратор | лише люди (запрошення), підрозділи, категорії, посади; хвиль і результатів не бачить |
| `department` | Департамент | конструктор анкет, версії, публікація; зведення закладів |
| `leader` | керівник | дашборд, результати, рішення щодо рекомендацій, заходи (усе дерево) |
| `leader_a` | керівник підрозділу А | те саме, але лише «Підрозділ А» і дочірні |
| `auditor` | внутрішній аудит | читання: результати, рекомендації, заходи, журнал; підтверджує пункти чек-листа й відкриття хвилі |
| `wg1`…`wg6` | учасник, робоча група | Анкета 1, внесення чек-листа, мої результати |
| `staff01`…`staff75` | учасник, особовий склад | Анкета 2, мої результати |
| `expert1`…`expert5` | учасник, експерт | Анкета 3, мої результати |

## Факти з інших систем (адаптери)

Моки 5 джерел (ARTEMIDA, атестація, навчання, закупівлі, повідомлення) передають факти «X з Y» у `POST /indicators`, кожне джерело своїм ключем
(деталі — [`backend.md`](backend.md), «Адаптери джерел фактів»). Задайте ключі в `.env`, наприклад
`INTEGRATION_KEYS=artemida=…;atestat=…;training=…;procurement=…;reports=…`, перезапустіть compose і виконайте:

```bash
docker compose exec backend python scripts/mock_sources.py --dry-run   # що буде передано
docker compose exec backend python scripts/mock_sources.py             # передати (12 місяців, усі 5 джерел)
docker compose --profile mocks run --rm mocks                         # те саме окремим контейнером (профіль mocks)
```

Нові факти видно в `GET /units/{id}/indicators` і в ризик-сигналах; знімки вже закритих хвиль не змінюються.

## Документи з прогону

`docs/recommendations.md` і `docs/cross-check.md` не пишуться вручну. Після змін у правилах, методиці чи seed:

```bash
cd backend && python scripts/gen_docs.py   # тимчасова SQLite-база, робоча БД не зачіпається; дата вивантаження фіксована
```

Поза Docker скрипт пише файли-докази в `EVIDENCE_DIR` (типово `/data/evidence`, як у контейнері). Якщо `backend/.env` немає,
задайте теку явно: `EVIDENCE_DIR=./data/evidence python scripts/gen_docs.py`.

## Перевірки

```bash
cd backend && pytest                    # бекенд: 443 тести (на SQLite 5 пропускаються: xmin і гонки — лише PostgreSQL)
TEST_DATABASE_URL=postgresql+psycopg://imd:пароль@localhost:5432/imd_test pytest   # те саме на PostgreSQL
cd frontend-proto && npm run build      # основний фронтенд: збірка без помилок (те саме робить CI)
cd backend && python scripts/export_openapi.py   # після змін API: оновити docs/api/openapi.json (потрібен DATABASE_URL з backend/.env; база не відкривається, достатньо sqlite:///./tmp.db)
```

`frontend-proto` не має власних юніт-тестів і лінтера; ручна перевірка екранів (ширини 1440 і 390, без горизонтального
скролу й `pageerror`) описана в `frontend-proto/CLAUDE.md`, розділ «Як робити правку».

> Після 5 невдалих спроб входу для пари логін + IP вхід блокується на 5 хвилин (429). Лічильник зберігається в БД
> (таблиця `login_failures`, лише хеші), тож переживає перезапуск і спільний для всіх процесів API: зачекайте 5 хвилин.
> Анонімні посилання: рахуються лише невірні (5 за 5 хвилин з однієї IP → 429 саме для невірних); дійсне посилання
> відкривається завжди, навіть з тієї ж адреси.
